# Phase 6 — UI

**Outcome:** the game is playable in a browser and behaves like the original. **This is the milestone that closes the port.** Ports `original/src/rogule/ui.cljs` (352 lines) and `original/public/css/style.css` (544 lines).

**Status: done, 2026-08-10.** Played start to finish in a browser and it behaves like the original. What landed differently from this plan is recorded in "How it came out" at the bottom; read that before the body, which is the pre-implementation sketch and is left as written.

[05a-simplify.md](05a-simplify.md) landed first, and this doc was reconciled with it. The shapes to write against are:

- **Entity behavior is `entity.kind`** — `'player' | 'monster' | 'shrine' | 'cover' | 'item' | 'potion'`, absent on the smoke puff and collision marker. There is no `entity.fns`.
- **Tiles are a flat numeric array.** `GameMap.floorTiles` is `Tile[]` indexed `y * w + x`; read it with `tileAt(map, x, y)` from `grid.ts`, which returns `TILE.rock` off the map. **Do not index it by hand** — a raw `y * w + x` on a negative `x` lands on the previous row. The tile→sprite/class mapping wants `TILE.room` / `TILE.wall` / `TILE.door` / `TILE.corridor`, not strings.
- **HP is `{ cur, max }`**, not the old `[current, max]` pair. The health bar iterates a range either way.
- The entity index still uses `"x,y"` string keys — see "Rendering model" below.
- **The engine's only `state → state` entry point is `takeTurn`** — and `engine/index.ts` still exports `moveTo` / `updateMonsters`, which 5.5 §6 turned into draft mutators the UI cannot call. First task of this phase: add the `expireAnimation` reducer (see "Animations") and prune those two exports.

### Step 0 — gate monster pathfinding before the keypress handler exists

Do this before any component is written. `chasePlayer` (`engine/monsters.ts`) builds the blocked set and runs a full A* from the monster to the player **for every living monster, every turn**, and only then checks `activation` — the cheap gate that rejects most of those paths. Measured over 100 turns of runSeed 3, the pathfinder emitted 7,551 path nodes, nearly all of them discarded.

This is not a bug and nothing currently notices. It becomes visible in this phase, because "every turn" turns into "inside the keypress handler", where the cost lands directly on input latency.

The shape of the fix is an early-out: `path.length` (inclusive of both ends) is never less than the manhattan distance, so a monster whose `|dx| + |dy|` already exceeds its `activation` cannot pass the gate, and can be skipped before `makeMonsterPassable` or `findPath` is called at all. `pos.ts` has a `distanceSq` that nothing uses yet; either it or a plain manhattan helper does the job.

**It does not work as a drop-in, and this is the part to get right.** `findPath` returns `[]` when there is no route, so an unreachable monster has `path.length === 0`, which passes `0 < activation` as though it were standing next to the player. That is not a rare corner: measured over 8 seeds × 60 turns, **322 of 1,925 monster-turns had no path** — `makeMonsterPassable` treats every occupied square as blocked, so monsters routinely wall each other off. Those turns currently draw from the RNG and then rest. A manhattan early-out would skip them, and since the chase and combat rolls share one stream, every seeded playthrough would shift.

So do it in two steps, in this order:

1. **Make "no path" mean "not activated"** — change the gate to `path.length > 0 && path.length < activation`. This is what the function's own docstring already claims ("a monster two squares away through a wall stays asleep"); a monster with no route at all being maximally awake is the opposite. This is the step that moves the RNG stream, so take the test churn here, on its own commit, where it is legible.
2. **Then add the manhattan early-out**, which after step 1 is exactly behavior-preserving: a distant reachable monster fails both the old and new gate, and an unreachable one fails both. It should be a pure speedup with no test churn at all — if step 2 changes a single seeded expectation, something is wrong.

Two further things a careless version breaks:

- **The RNG short-circuit.** `&&` means a monster failing the distance half never draws; `chasePlayer`'s docstring already calls this out. The early-out must return *before* touching `rng`.
- **Diagonal geometry.** Manhattan is an admissible lower bound for 4-way movement only. If monster movement ever goes 8-way, this bound must become Chebyshev or the early-out starts skipping monsters that could in fact reach the player.

Pin it with tests that a monster outside its activation radius is left alone, that one just inside still chases, and that a walled-off monster does not chase — all against a fixed seed.

## Rendering model

The board renders a `2 * visibleDist` square window centered on the player (`visibleDist` 9, so 18×18 cells), not the whole 32×32 map. Cells outside `clearDist` (7) render at 0.75 opacity, outside `visibleDist` at 0. That opacity gradient is the fog of war — there is no separate visibility computation.

Re-rendering the whole window every keypress is fine. It is turn-based, ~324 cells, and the original does exactly this. Do not add virtualization.

`entitiesByPos` (phase 3) builds a `"x,y" → Layer → Entity[]` index, memoized per `entities` object identity in a `WeakMap` — one build per state change, however many renders read it. **Entities are keyed by string; tiles are addressed by array index.** The two representations are independent on purpose (5.5 §3 flattened the tile map and left this one alone, because it is rebuilt per turn and never persisted), so a cell renders by looking up `entitiesAt(index, posKey(x, y))` for its contents and `tileAt(map, x, y)` for its floor. Don't try to unify them.

The memo makes re-renders of an unchanged state free. It does *not* make updates cheap — every turn moves the player, so the index rebuilds every turn regardless. Rebuilding ~40 entries is microseconds; don't design around it. Cells call `entitiesAt`, which flattens a cell in layer order `floor, between, occupy, above` with dead entities sorted below living ones in each layer, so corpses appear under items. Don't re-derive any of that ordering in JSX — it's already done.

## Keyboard input

The original attaches listeners via a Reagent ref callback and stashes the handler on `window._game-key-handler` to remove it later. In React, this is a `useEffect` with a cleanup return — the stashing hack is unnecessary.

Key codes from `key-dir-map`: arrows (37/39/38/40) and vim keys (h/l/k/j = 72/76/75/74), plus `.` (190) to rest. Also `?` (191) toggles help and `Esc` (27) closes it. The handler maps keys to `Dir` (from `engine/movement.ts`, phase 5) and calls `takeTurn(state, dir, rng)` — the combat `Rng` is created once per level from ambient entropy (`makeRng(randomSeed)`; entropy is injected at the edge, per PLAN.md) and held in the UI layer (a ref, not state); see phase 5's "The RNG is injected".

The help-open flag is UI-local `useState` in App, not `GameState` — the original kept `:modal` in its one big persisted atom (`ui.cljs:326-327`), but a help overlay has no business surviving a reload. There is no message line or pickup modal to port: both are dead code in the original and their fields were dropped from the types (see phase 5's omissions).

`keyCode` is deprecated but works everywhere and the original uses it. Port to `event.key` instead — it is clearer (`'ArrowLeft'`, `'h'`, `'.'`) and the on-screen arrow buttons stop needing synthetic `KeyboardEvent`s with fake keycodes, which is the ugliest part of the original UI (`trigger-key`). Have the buttons call the same `takeTurn` action the keyboard handler calls.

## Animations

Entities carry `animation: Animation` — an object `{ name, disposal?, frame? }` (`types.ts`), not the original's `[name, disposal, frame]` tuple. Two mechanisms:

- **Bump.** `move-to` sets `bump-left|right|up|down` when a move is blocked. Pure CSS, keyed off a class.
- **Destroy-on-end.** Smoke puffs and collision markers carry `disposal: 'destroy'`; the `onAnimationEnd` handler removes the entity from state. Port this — it is how transient effects get cleaned up. The removal goes through `expireAnimation(state, id): GameState`, a one-line `produce` around `removeEntity` added to the engine surface by this phase — the engine's second entry point. 5.5 §6's "one `produce`" rule is per *entry point*, not per codebase ("The reducer phase 6 needs" there spells this out); do not import Immer in the UI or hand-spread the state instead.

`replay-pop-animation-on-change` in `emoji.cljs` is a DOM hack to restart a CSS animation by removing the class, forcing reflow via `offsetHeight`, then re-adding it. It relies on the sprite being an `<img>` with an `onload`. Since sprites are now URL-referenced files that may be cached (no reliable `onload`), re-implement this as a React `key` change instead — changing the key remounts the element and restarts the animation, which is the idiomatic equivalent and less fragile. `Animation.frame` exists for exactly this: include it in the key. The original sets it to the move counter on each bump (`engine.cljs:83`), which is what makes a repeated bump replay.

## Health bars

One trap inherited from the id migration: the original memoizes `component-health-bar` on entity *copies* (`ui.cljs:91`), which self-refreshed because combat re-copied combatants each round. `state.combatants` now holds stable ids while HP changes underneath, so a `React.memo` keyed on the id renders stale bars forever. Memoize on `(id, hp)` or not at all — 324 turn-based cells don't need it. And per phase 5: skip combatant ids that no longer resolve in `state.entities`.

## CSS

`style.css` is mostly self-contained and ports as-is. Strip: the landing-page styles (`body.page`), the ad block, and the `#loading` spinner. Keep the grid, tile, animation, health bar, and modal rules.

## Tombstone / share string

`make-share-string` builds the emoji summary two ways from one function — passing either `emoj` (text characters, for clipboard) or `tile-mem` (image elements, for display), with `"\n"` or `<br/>` as the separator. That is a nice bit of factoring; keep the shape, typed as a generic over the render target.

The original's version reads `:statistics` out of game state (`ui.cljs:193`, `210`); statistics are run-scoped now, so the ported function takes `(state, statistics)`. Until phase 7 introduces the persistent run layer, App holds a transient in-memory `Statistics` (via `emptyStatistics()`, reset on reload) — fine for the phase-6 milestone; phase 7 makes it durable.

Drop from the tombstone: the social-media search links (Mastodon/Bluesky/Threads/X), the `component-game-ad` block, and the feedback mailto. Keep the stats block and the share button — though note that phase 7 replaces the "next rogule" countdown with the pomodoro timer, and phase 8 makes the whole tombstone appear only on death rather than on every level completion.

## Definition of done

Play a full level start to finish: move, fight a monster, take damage, pick up items, uncover a cover, die on purpose, then win by reaching the shrine. Compare against the original running side by side if anything feels off. Do not start phase 7 until this passes.

## How it came out

Step 0 took the two commits it was specced to take, and behaved exactly as predicted: step 1 moved the RNG stream and cost one test, step 2 changed nothing at all (12 seeds × 300 turns, byte-identical states) and cut the turn loop from 2146ms to 469ms. The one surprise was in the *test*, not the code — see "the walled-off monster" below.

Six things worth knowing that the sketch above did not say:

1. **The walled-off monster is only observable in the RNG stream.** The obvious test — seal a monster off, assert it stays put — passes with or without the fix, because the old gate handed `moveTo` an empty path, which it read as a rest. The monster held still either way. What actually changed is that it no longer *rolls*, so the test counts draws instead of positions (`countingRng` in engine.test.ts). Any future test of an activation gate wants the same treatment.

2. **`reaches the shrine when walked straight to it` was a coin flip.** It walks a level-1 player down a path with no tactics, and 5 of the first 10 dice seeds died en route — for a test whose subject is geometry. It now gives the player hp headroom, which descends on all 48 (runSeed, diceSeed) pairs surveyed. Seed-hunting would have re-broken on the next RNG change.

3. **Entities must render even at opacity 0.** The original does this and it looks like an oversight; it is not. An invisible entity's CSS animation still runs and still fires `animationend`, which is what removes spent smoke and collision markers. Skipping the dark cells leaks every effect that expires off-screen.

4. **The fog opacity is applied once, not twice.** The original sets it on the cell *and* passes it to each entity tile, compounding to 0.5625 in the dim ring. This renders the 0.75 the doc describes.

5. **Health-bar replay had to be asked for.** In the original, `pop` replayed because combat re-copied its combatants every round and the memoized component remounted. With stable ids the remount has to be explicit: the bar's React key carries `hp.cur`.

6. **The `?` and `.` keys collide with browser chrome.** The handler skips anything carrying a modifier (⌘R is a reload, not a rest) and calls `preventDefault` only for keys the game actually claimed.

Left undone on purpose, each with a home:

- **No component tests, and no jsdom.** `vite.config.ts` still says phase 6 will need it. The share string got a test because it is pure logic whose output is a claim about someone's run; the rest of the UI is layout, and its check is looking at it. If phase 7's timer logic grows conditionals, that is the moment to add jsdom — not before.
- **Statistics are transient**, held in `App` and wiped by a reload, as this doc specified. Phase 7 owns making them durable, and `recordOutcome`'s "one level is one run" assumption dies with phase 8.
- **The tombstone shows on every outcome**, with a "play again" button where the original's countdown was. Phase 7 puts the pomodoro timer there; phase 8 makes a cleared level roll on to the next depth instead.
